Вывод для Voxy

Следующий большой шаг — связать уже существующие GPU-модули управлением ресурсами и очередями: общий учёт памяти, ограниченный пул readback, явная передача compute-результата renderer и безопасное повторное использование после завершения GPU. CUDA следует развивать как отдельный аппаратный путь с проверкой устройства и синхронизации.

Что подтверждают исходники

  1. Проходы описывают доступ к данным. Godot выводит барьеры из usage и write dependencies; Blender учитывает используемые buffers при перестановке команд. В Voxy нужен общий контракт producer/consumer проходов. Внутри wgpu часть tracking уже реализована: дублировать её вручную не следует.
  2. Ресурсы освобождают по завершению работы. wgpu LifetimeTracker, Flax deferred deletion, DirectXTK12 pending pages и Filament command pools отделяют CPU ownership от GPU completion. Счётчик кадров сам по себе недостаточен для межочередного interop.
  3. Readback — отдельный, ограниченный поток. Bevy держит requested/mapped очереди и возвращает буфер в pool после результата; melonJS учитывает row alignment. Для Voxy полезно оставить nonblocking API и добавить reuse/backpressure.
  4. Compute может кормить renderer без копирования на CPU. bgfx показывает culling → compaction → indirect draw; The Forge переводит particle buffers между UAV и indirect/shader states; three.js поддерживает indirect compute dispatch.
  5. Бюджет — не только размер пользовательских данных. VMA и D3D12MA различают allocations, heap/block usage и доступный бюджет; gpu-allocator различает allocated bytes и block capacity. В бюджет Voxy должны попасть staging, scratch, history, geometry и сохранённые в RAM чанки.
  6. Recovery восстанавливает зависимые объекты. PixiJS пересоздаёт свой device и рассылает contextChange, но не присваивает себе recovery чужого shared device. Urho3D убирает потерянную surface из FBO caches.

Эти выводы — интерпретация просмотренных участков. Конкретные файлы и закреплённые commits находятся в таблице ниже. Mirrors Unity перекрываются с Unity Graphics: 100 репозиториев не означает 100 независимых архитектур. Старые примеры и archived проекты учитываются как инженерные примеры, а не как актуальные рекомендации зависимостей.

Что говорят форумы и где проверено правило

  • GameDev.net: CPU/GPU synchronization — ring buffers и несколько кадров в обработке; объяснение 2011 года относится к API того времени. Для современных lifetime правил использован Khronos: Resource Lifetimes.
  • GameDev.net: Shader Permutations — варианты зависят от mesh, material и pass; обсуждение автора OGRE. Для Voxy ключ pipeline следует описывать полными свойствами, а не одним непроверяемым hash.
  • Khronos Forum: voxel counting и workgroup synchronization — barrier внутри dispatch не создаёт глобальный порядок между workgroups. Для отдельных проходов проверены официальные примеры synchronization. Это особенно важно при распараллеливании ordered water solver.
  • Godot Forum: compute texture → экран — показан конфликт local/main RenderingDevice и лишний readback; часть предложенного native-handle sharing на форуме не является универсально проверенным решением. В официальном compute tutorial немедленный sync выделен как блокирующий учебный путь.
  • NVIDIA Forum: wait-before-signal deadlock — обсуждение ограничения external semaphore imports. CUDA Programming Guide подтверждает необходимость matching device UUID, корректных mappings и порядка signals/waits. Правила Vulkan timeline нельзя автоматически переносить на CUDA imports.
  • Khronos Forum: memory/texture barriers — различает incoherent writes и feedback при render-to-texture. Нельзя вставлять одинаковый универсальный barrier для всех backend.

4CUDA interop: сохранить уже существующие UUID/LUID проверки, исследовать persistent imports и external semaphore handoff вместо повторного import/synchronize в publish.Физическая NVIDIA; Vulkan и DX12 отдельно; несколько кадров, ошибки, shutdown и несовпадающие устройства. 5Capability profiles и shader/pipeline artifacts: реальные features/limits/formats, стадии, layouts, precision policy, options и target. Warmup отдельно от rendering.Неподдерживаемая комбинация отвергается или выбирает проверенный путь; failed compile сохраняет предыдущий рабочий pipeline.
6Реальное recovery renderer + world state; затем platform acceptance на desktop/mobile/XR.После device loss сохранены edits и pending-work semantics, ресурсы созданы заново; физические устройства подтверждают поддержку.

Базовые места в текущем Voxy проверены чтением исходников: ComputeJob::encode_snapshot и ComputeDispatch::copy_buffer создают staging; VulkanGravityInterop::publish проверяет ownership и использует import/release/synchronize/acquire; Vulkan UUID и DX12 LUID checks уже есть. Эти рекомендации не утверждают отсутствия всех механизмов и не являются результатами performance benchmark.
