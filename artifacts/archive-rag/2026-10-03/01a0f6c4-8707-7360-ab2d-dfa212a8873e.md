Да. Для скриптов поведения Voxy в Rush прежде всего не хватает **постоянного экземпляра скрипта и вызова его функций из Rust**. По текущему коду каждый `Program::run` создаёт новое состояние.

Я бы добавил в Rush:

1. **`ScriptInstance` с сохранением переменных между вызовами.** Чтобы здоровье, таймеры и состояние поведения жили между кадрами.
2. **Вызов именованных функций из Rust:** `start()`, `update(delta)`, `fixed_update(delta)`, обработчиков событий. Сейчас публичный API запускает программу целиком.
3. **Контекст для host-функций.** Сейчас callback — обычный указатель `fn`, без захваченного контекста. Нужен удобный доступ к конкретной сцене и очереди команд без глобальных переменных.
4. **Передачу произвольных `Value` как входных параметров.** Сейчас входы `run` только числовые; для Voxy нужны ссылки на объекты, события и структуры данных.

Уже есть полезная основа: `HostObject`, типизированные host-функции, векторы, кватернионы, матрицы, модули, бюджет операций и отмена.

А `spawn`, трансформации, компоненты, ввод, физику и подписки на события нужно реализовать **в привязках Voxy**. Самому Rush достаточно универсального механизма работы с ними.

Начал бы с пунктов 1–4: они позволят писать обычные скрипты поведения вместо пересчёта позиции отдельным выражением.

Дальше стоит довести Rush до полноценного языка поведения объектов Voxy. Возможностей runtime уже достаточно; сейчас основная работа — интеграция.

1. **Менеджер скриптов.** Загружать `.r`, создавать отдельный `OwnedScriptInstance` для каждого объекта, вызывать `start`, `update(delta)`, `fixed_update(delta)` и `on_destroy`. Переменные должны сохраняться между кадрами.

2. **Минимальный API сцены.** Дать скрипту `self`, чтение и изменение трансформации, поиск объектов, создание и удаление. Использовать проверяемые handles Voxy; изменения передавать через очередь команд.

3. **Ошибки и диагностика.** Показывать файл, строку и стек вызовов. При ошибке отбрасывать команды обработчика и приостанавливать экземпляр, чтобы он не повторял ошибку каждый кадр.

4. **Ввод и события.** Подключить действия ввода, события сцены и доступные события физики. Сделать демонстрацию: игрок движется, создаёт объект, реагирует на событие.

5. **Перезагрузка и сохранения.** Перекомпилировать изменённый `.r`, переносить явно выбранное состояние. Если новый скрипт не компилируется, оставлять предыдущий работающий экземпляр.

Начал бы с **менеджера и API сцены**, проверяя их на одном примере:

```text
mut elapsed = 0

    set_position(self, vec3(0, 1, 0))
}

fn update(delta: f64) {
    elapsed += delta
    translate(self, vec3(delta * 2, 0, 0))
}
```

Это предлагаемый API. Первый законченный результат: два объекта с одним `.r`, независимым состоянием и движением в запущенной сцене. После этого расширять компоненты и физику по потребностям конкретных скриптов.

Для самого Rush я бы развивал язык в таком порядке:

1. **Типы пользовательских данных:** `struct` и `enum`, проверка полей и исчерпывающий `match`. Это позволит описывать состояния, события и настройки без произвольных строковых ключей.

2. **Проверка типов до исполнения.** Вывод типов локальных переменных, проверка аргументов, возвращаемых значений и операций. Ошибки должны обнаруживаться при загрузке скрипта, включая код ещё не выполненных веток.

3. **Обработка ожидаемых ошибок:** `Result`, `Option` и оператор `?`. Отсутствующий объект или неудачный поиск должны быть обычным результатом, который скрипт может обработать.

4. **Явная система модулей.** Экспорты, приватные имена, пространства имён и понятные правила циклических импортов. Нужна для библиотек из нескольких `.r`.

5. **Корутины и приостановка выполнения.** Например, ждать событие или несколько секунд, сохраняя локальное состояние. Сначала определить семантику отмены и возобновления; затем вводить синтаксис.

6. **Инструменты разработки:** форматирование, навигация, переименование, автодополнение и диагностика с теми же правилами, что у исполнителя.

Начал бы с **типов данных и статической проверки типов**. Они дадут больше пользы для растущих скриптов, чем добавление новых сокращений синтаксиса. Это направления развития; наличие каждого механизма в последнем обновлении нужно отдельно проверить.
